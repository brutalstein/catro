# Cross-platform releases and one-command installers — design

Date: 2026-09-30
Status: approved in chat; written review pending

## 1. Goal

Publish reproducible Catro downloads through GitHub Releases and provide one terminal command that
downloads, verifies, and installs the correct package on Windows or macOS without requiring users to
clone the repository or install build tools.

This is the first of two independent delivery milestones:

1. this design: release automation, checksums, installers, download documentation, and a Windows
   production package plus an explicitly labeled macOS preview package;
2. a follow-up design: native macOS room, Internet voice, and screen-sharing parity.

The macOS package must not be described as voice/screen compatible until the follow-up milestone has
passed its own implementation and real-machine acceptance gates.

## 2. Existing baseline

- `scripts/package-windows.ps1` already builds a self-contained Windows x64 ZIP, validates the
  production HTTPS service URL, writes `catro-network.json`, and emits a SHA-256 file.
- The Windows shell already uses the deployed Catro service for authenticated rooms, voice, and
  screen sharing.
- `scripts/build.sh Release` already builds `Catro.app` on macOS.
- GitHub CI already builds and tests Windows, Apple Silicon macOS, Intel macOS, signaling, sanitizers,
  and deployment configuration.
- No release workflow, macOS package script, one-command installer, GitHub Release, or published tag
  currently exists.
- The macOS SwiftUI app currently provides diagnostics and local audio tests only.

The release work extends these boundaries instead of introducing a new package manager, update
service, signing service, or website.

## 3. User-visible contract

### Windows

The documented install command is:

```powershell
irm https://github.com/brutalstein/catro/releases/latest/download/install-windows.ps1 | iex
```

It installs the latest stable Windows x64 package under:

```text
%LOCALAPPDATA%\Programs\Catro
```

The installer prints the installed version and executable path. A repeated run upgrades the existing
installation. User identity and room state stored outside the installation directory remain intact.

### macOS

The documented install command is:

```sh
curl -fsSL https://github.com/brutalstein/catro/releases/latest/download/install-macos.sh | sh
```

It selects the Apple Silicon or Intel package from `uname -m` and installs under:

```text
~/Applications/Catro.app
```

Until native room/media parity is complete, the command and release notes identify this application
as **Catro macOS Preview — diagnostics and local audio testing**. They explicitly state that this
preview does not yet join production voice rooms or send/receive screen sharing.

The free package is ad-hoc signed rather than Developer ID signed or notarized. The installer never
disables Gatekeeper, removes quarantine metadata, changes system security policy, or silently grants
privacy permissions. Documentation explains the normal macOS user approval flow and the separate
Microphone and Screen Recording permissions required by future media builds.

## 4. Release assets

Every stable release uses the same fixed asset names so the `latest/download` URLs remain durable:

```text
Catro-windows-x64.zip
Catro-windows-x64.zip.sha256
Catro-macos-arm64-preview.zip
Catro-macos-arm64-preview.zip.sha256
Catro-macos-x64-preview.zip
Catro-macos-x64-preview.zip.sha256
install-windows.ps1
install-macos.sh
```

The preview suffix remains in macOS asset names until the native parity milestone is accepted. That
milestone may replace the preview assets with stable names, but this release design does not reserve
or publish misleading stable macOS filenames early.

Release source archives generated by GitHub remain available but are not end-user application
packages.

## 5. Release workflow

A dedicated `.github/workflows/release.yml` runs on tags matching `v*` and supports
`workflow_dispatch` for packaging validation without publication. A tag is valid only when it is
exactly `v` followed by the root CMake project version, for example `v0.1.0`.

The workflow contains four bounded jobs:

1. **Windows package**
   - checks out the tagged commit;
   - runs the existing bootstrap, Release build, and Windows tests;
   - runs `scripts/package-windows.ps1` with
     `https://51-170-186-61.sslip.io`;
   - uploads the ZIP and checksum as a workflow artifact.
2. **macOS package matrix**
   - runs on `macos-15` and `macos-15-intel`;
   - runs bootstrap, Release build, and tests;
   - packages only the matching architecture;
   - applies ad-hoc signing to the finished `.app`;
   - uploads the architecture-specific preview ZIP and checksum.
3. **Service validation**
   - runs signaling tests, race tests, vet, and build;
   - runs deployment shellcheck, static verification, Compose validation, and Windows production
     endpoint-policy validation;
   - uploads no release asset.
4. **Publish**
   - runs only for a valid `v*` tag after both package jobs and service validation succeed;
   - downloads the exact job artifacts;
   - adds the two installer scripts;
   - creates a draft GitHub Release for the tag;
   - uploads and verifies the complete expected asset set while the release remains private;
   - publishes the draft only after every asset and checksum is present;
   - leaves a failed upload as a draft rather than exposing a partial public release;
   - fails instead of mutating an already published release for the same tag.

Only the publish job receives `contents: write`; all build jobs retain read-only repository access.
The workflow uses GitHub-maintained checkout and artifact actions plus the runner-provided `gh` CLI.
No marketplace release action or external release service is introduced.

`workflow_dispatch` builds and preserves workflow artifacts but does not create a GitHub Release. It
is the pre-tag rehearsal path.

## 6. macOS package boundary

`scripts/package-macos.sh` owns macOS packaging:

- accepts `Release` by default;
- uses the selected CMake preset and verifies the built `Catro.app`;
- accepts only `arm64` or `x86_64` output matching the runner architecture;
- copies the bundle into an empty staging directory;
- applies `codesign --force --deep --sign -` for an ad-hoc signature;
- verifies the resulting bundle with `codesign --verify --deep --strict`;
- creates the fixed preview ZIP name;
- writes a lowercase SHA-256 file in the same two-column format as the Windows package;
- writes only under `out/dist`;
- fails before producing a final ZIP when the app, helper executable, architecture, or signature
  validation is wrong.

The script does not require an Apple account, certificate, keychain secret, paid Apple Developer
Program membership, or notarization credential.

The package includes a short README that identifies the preview feature boundary and the pinned
minimum supported version, macOS 13.0.

## 7. Installer behavior

Both installers implement the same transaction:

1. resolve the requested version, defaulting to the latest non-draft, non-prerelease GitHub Release;
2. select the exact platform asset and its checksum;
3. download both over HTTPS into a newly created temporary directory;
4. parse only a strict 64-character hexadecimal SHA-256 value;
5. hash the downloaded archive and compare without case sensitivity;
6. extract into a second temporary staging directory;
7. validate the expected executable or app bundle before touching the current installation;
8. move the current installation to a temporary backup;
9. move the validated staging installation into place;
10. restore the backup if replacement fails;
11. remove temporary files and the successful backup;
12. print the installed version and launch path.

Neither installer runs the downloaded application automatically.

### Windows-specific rules

- Requires Windows PowerShell 5.1 or PowerShell 7.
- Supports x64 only and fails with an explicit architecture message elsewhere.
- Uses built-in PowerShell, .NET ZIP support, `Invoke-WebRequest`, and `Get-FileHash`.
- Does not require administrator privileges or modify machine-wide directories.
- Creates a Start Menu shortcut only if native PowerShell/COM support succeeds; shortcut failure does
  not invalidate an otherwise complete installation.
- Never writes credentials or release tokens.

### macOS-specific rules

- Requires `curl`, `shasum`, `ditto`, and `uname`, which are provided by supported macOS versions.
- Supports `arm64` and `x86_64`; other architectures fail explicitly.
- Does not use `sudo`.
- Preserves quarantine metadata and does not execute `xattr`, `spctl --master-disable`, or equivalent
  security-bypass commands.
- Does not claim that an ad-hoc signature establishes publisher identity.

## 8. Testability

Production installer URLs remain fixed, but deterministic tests must not depend on a live GitHub
Release. Each installer therefore accepts test-only environment overrides for:

- release base URL;
- installation root;
- requested version.

The public one-line commands set none of these values.

Fixture tests serve static release files from a local HTTP server and verify:

- correct Windows and macOS architecture selection;
- successful first install;
- successful replacement of an existing install;
- preservation/restoration of the old install when replacement fails;
- rejection of a malformed checksum;
- rejection of a valid but mismatched checksum;
- rejection of a missing expected executable or app bundle;
- cleanup of temporary state;
- no launch after installation;
- no mutation outside the overridden installation root.

macOS package validation also inspects the archive architecture and ad-hoc signature. Windows package
validation continues to inspect its production network configuration and required runtime files.

## 9. Documentation

The root README gains a Download and install section near the top:

- direct Windows package link;
- Windows one-line install command;
- Apple Silicon and Intel macOS preview package links;
- macOS one-line install command;
- SHA-256 verification instructions;
- supported platform/architecture table;
- current Windows production feature list;
- current macOS preview limitation;
- unsigned/ad-hoc macOS Gatekeeper explanation;
- deployed service status URL;
- uninstall paths;
- a statement that screen sharing consumes system and network resources and cannot promise zero game
  impact.

The Oracle deployment README links back to the release workflow but does not become responsible for
desktop installation.

## 10. Security and failure behavior

- All production release and installer downloads use HTTPS GitHub URLs.
- Checksums detect corruption and asset mix-ups; they are not described as protection from a
  compromised GitHub repository or maintainer account because the archive and checksum share the same
  trust origin.
- A failed checksum, extraction, architecture check, signature check, or expected-file check leaves
  the current installation unchanged.
- Existing installations are replaced only after the staged package passes validation.
- Installer errors are non-zero and actionable; they do not fall back to unverified packages.
- Release jobs never print GitHub tokens or package private credentials.
- No Oracle SSH key, TURN secret, signaling secret, room token, invite code, or local identity is
  included in release assets.
- The Windows package contains only the public HTTPS service endpoint.

## 11. Release readiness gates

A tagged release is eligible for publication only when:

1. Windows Release build and tests pass.
2. Apple Silicon and Intel Release builds and tests pass.
3. Signaling and deployment CI remain green for the same source revision.
4. Both package scripts validate their final archives.
5. Installer fixture tests pass on their native operating systems.
6. The Windows package points to `https://51-170-186-61.sslip.io`.
7. A fresh HTTPS health request and WSS upgrade against the production service pass.
8. Release asset checksums match after downloading the published assets.

The first release is not described as real-machine cross-city acceptance evidence until two external
Windows computers have completed voice and screen-sharing tests. Infrastructure health, TURN relay
tests, and hosted CI are necessary but do not replace that user-path test.

The macOS preview is not promoted to stable until the separate native parity milestone proves:

- production room join on Apple Silicon and Intel;
- simultaneous voice with Windows and macOS peers;
- screen video send and receive;
- selected-screen or selected-window capture;
- system/application audio behavior documented for the supported macOS versions;
- direct ICE and forced TURN operation;
- permission denial and revocation recovery;
- real-machine CPU, GPU, memory, and frame-drop measurements.

## 12. Performance claims

This milestone does not rewrite the Windows media pipeline. Existing hardware H.264 encoding,
bounded queues, frame dropping, capture throttling, and reduced preview work remain the production
baseline.

Release notes may say that Catro is designed to minimize game impact with hardware acceleration.
They must not say screen sharing has zero performance cost or can never affect a game.

Any later change to capture resolution, frame rate, bitrate, thread priority, encoder fallback, or
adaptive quality requires measured evidence and belongs to the platform media milestone, not the
installer.

## 13. Non-goals

- Microsoft Store, Mac App Store, Homebrew, WinGet, DMG, PKG, MSI, MSIX, Sparkle, or a custom updater.
- Automatic background updates.
- Paid code-signing certificates or Apple notarization.
- Disabling Windows or macOS security controls.
- Universal macOS binaries; the release publishes one native package per architecture.
- Claiming macOS voice or screen-sharing parity before it exists.
- Replacing GitHub Releases with a custom download service.
- Changing the Oracle deployment topology.
- Changing media codecs, signaling protocol, room capacity, or TURN configuration.

## 14. Follow-up milestone

After this release milestone is implemented and verified, the next architectural design will cover
native macOS production parity. It will reuse the existing authenticated service and shared portable
voice/video/transport cores, while adding the minimum macOS-specific room shell, RTC integration,
screen capture, hardware video encode/decode, presentation, and permission handling needed to
interoperate with Windows clients.

That work receives its own spec and implementation plan because it changes the application
architecture and real-time media boundaries; it is not hidden inside packaging work.
