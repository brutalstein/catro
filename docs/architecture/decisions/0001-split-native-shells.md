# 0001: Split native shells over a shared C++ core

Status: accepted, 2026-09-26

## Context

Catro needs a native look and feel, native accessibility, and direct access to GPU, display,
encoder, and audio APIs on Windows and macOS. Cross-platform UI runtimes such as Electron, Qt, or
an embedded browser would add a second runtime and hide the platform APIs.

## Decision

- Each platform gets its own shell. Windows uses WinUI 3 with C++/WinRT, and macOS uses SwiftUI.
- The shells share a portable C++20 core. The core holds the capability model, policy, and
  reporting.
- They also share one plain C++ diagnostics view model (`apps/diagnostics`), so both shells show
  the same presentation. The Windows shell uses it directly. On macOS, a narrow Objective-C++
  bridge copies it into immutable Objective-C value objects for Swift.
- No C++ type, CoreFoundation reference, or Metal object crosses the Swift boundary.
- The macOS app is generated by CMake (Xcode generator) instead of a checked-in `.xcodeproj`. It
  links the core targets directly.

## Consequences

- Each shell's UI code is written twice. Presentation logic lives once, in C++, and is testable on
  any platform.
- The Windows shell is an MSBuild project because the XAML compiler needs it. It links the
  CMake-built static libraries through `CatroCoreRoot`.
- There is no stable binary ABI between components. All boundaries are static libraries or source.
